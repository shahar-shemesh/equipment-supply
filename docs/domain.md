# Domain model and server rules

## Domain model

The spec and the designs use "issuance" (הנפקה) for several different things, so the schema separates them:

- **Issuance** (`issuances`): the SAP document. Who the customer is, where it goes, the priority. Exists whether or not anyone was sent to deliver it. Its status mirrors the latest delivery outcome. Its `revision` is the concurrency token of an offline delivery report, see [What invalidates a report](offline-sync.md#what-invalidates-a-report).
- **Issuance item** (`issuance_items`): one product line of the document, with catalog number, station number and serial. The courier answers delivered / not delivered per line, which is where partial delivery comes from. A line the manager took off (`DELETE /issuances/:id/items/:itemId`) keeps its row with `removed_at` set: `delivery_attempt_items.item_id` points at it with no foreign key, so a past attempt keeps its reference, and the TypeORM delete date column leaves it out of every issuance and task load.
- **Delivery task** (`delivery_tasks`): "go deliver issuance X", one issuance handed to one courier for a date. This is what the courier's board lists. Reassigning cancels the old task and creates a new one, so the history of who had it stays. A self pickup handover writes a task with no courier (`courier_id` null, born done): the manager handed over at the warehouse and the attempt needs a task to hang off; no courier board ever lists it.
- **Courier** (`couriers`): whoever drives the equipment. Separate from `users`: a courier exists before anyone gives them a login (the sample data has two external companies without one).
- **Delivery attempt** (`delivery_attempts` + `delivery_attempt_items`): what the courier reported at the door: a result and reason per item, and who received plus the signature when at least one item was handed over. For a `not_delivered` attempt the four recipient columns and the signature are null: no one received and no one signed, so the screen never asked. Today one attempt closes a task; the table is ready for several attempts per task if "try again tomorrow" becomes a rule. `reported_at` is the server receipt time; `client_reported_at` is the device clock when the courier tapped send, kept separately because it is untrusted and can be hours earlier after an outage.
- **Delivery operation** (`delivery_operations`): the receipt of a report sent with an operation id: the account, the task, the attempt it created, a hash of the validated payload and the exact result body. The same id from the same account is answered with the stored result instead of a second attempt. Only successful reports get a row, and the row goes in the same transaction as the attempt.
- **Delivery conflict** (`delivery_conflicts`): a report the attempts route refused with a 409, handed over by the tablet as evidence: the account and courier (from the token), the original task and issuance, the revision the report was written against, the answers, the recipient and the signature (null when the signed report delivered nothing, the same rule as an attempt), the device time, a hash of the content, the rejection code and the authoritative state the server saw when it recorded it (`observed`). Review fields (`review_status`, `reviewed_by`, `reviewed_at`, `review_note`, `review_version`) are the manager's acknowledgment and sit apart from the submitted content, which never changes. Nothing here is a delivery: no attempt, no task close, no issuance status, no revision bump. Unique per (account, operation id).
- **Audit log** (`audit_log`): one row per committed state change. Who: `actor_type` (`user` or `system`), `actor_user_id`, `actor_username` and `actor_role`, copied at write time with no foreign key, so the row reads the same after a rename or a delete. What: `action` from the closed list `AuditAction` in `shared/@core.ts`, `entity_type` and `entity_id`. On which issuance: `issuance_id`, set on every row that concerns one, the delivery and conflict rows included, so the history of an issuance is one indexed query. In which bulk action: `batch_id`, shared by the rows of one assign, mark urgent or remove couriers. `details` holds ids and short scalars only: never a signature, a password hash or a whole payload (`audit.service` cuts strings at 200 characters and drops the key `signature_png`). Written by `server/src/audit/audit.service.ts` on the caller's transaction, after the mutation and without a lock, so a rolled back request leaves no row and a committed one always has one. Indexed by (`issuance_id`, `at`), (`actor_user_id`, `at`), (`entity_type`, `entity_id`, `at`) and (`at`).
- **XML export outbox** (`xml_outbox`): one row per committed issuance status change, the transactional outbox of the export to S3 ([XML export](xml-export.md)). `issuance_id` and `sequence` (1, 2, 3... per issuance in commit order, unique together), `previous_status`, `new_status`, `trigger` (the audit action of the same change), `occurred_at`, and `payload`: a snapshot with seven fields of the issuance after the change, the actor and a few ids and counts, never the customer, so the worker never reads `issuances`. The queue columns: `status` (`pending`, `processing`, `completed`, `failed`), `attempts`, `next_retry_at`, `lease_until`, `processed_at`, `s3_key`, `content_sha256`, `last_error`. Uuid primary key (`gen_random_uuid()`), no foreign keys for the same reason as the audit log. Written by `server/src/xml-export/xml-outbox.service.ts` on the caller's transaction after the audit row, without a lock. Indexed by (`status`, `next_retry_at`), (`issuance_id`, `sequence`) unique and (`status`, `lease_until`).
- **XML import files** (`xml_import_files`): one row per XML document the import ETL (`etls/issuance-xml-import/`, its [README](../etls/issuance-xml-import/README.md)) has seen, keyed by the SHA-256 of the bytes (`content_sha256`, unique): the same content under any file name is one row, so a copy dropped twice is imported once. `document_id` (the document's `DocumentId`, unique, set on completion), `file_name`, `size_bytes`, the claim (`status` `processing` / `completed` / `failed`, `instance_id`, `lease_until`, `attempts`), the outcome (`error_kind` `permanent` / `retryable`, `inserted` / `updated` / `unchanged`, `last_error`, `started_at`, `finished_at`). Uuid primary key, no foreign keys: the row outlives the issuances it touched. The server never writes it; the entity lives on the server side so `synchronize` and the migration create the table and the parity spec guards it. The ETL inserts issuances with `source = 'sap'` and writes one `audit_log` row per inserted or updated issuance (`actor_type` `system`, `action` `issuance.import`, `batch_id` the file row's id); it never writes `status` or `xml_outbox`.

Issuance statuses (`IssuanceStatus` in `shared/@core.ts`): `unassigned`, `assigned` (the courier sees it as waiting), `delivered`, `partially_delivered`, `not_delivered`, `self_pickup`, `deleted` (soft delete with a reason).

Terminology in the code follows the designers, not the original spec: issuance (not ניפוק), courier for משנע, warehouse manager for מנהל מחסן.

## Rules enforced on the server

**Status transitions.** `shared/@rules.ts` says from which status each manager action is allowed; `server/src/issuances/issuance.rules.ts` turns a refusal into the 409 and the manager board reads the same table to disable the button first (the kebab, the detail dialog and the selection checkbox). The 409 body is `{ statusCode: 409, message, code: 'status_not_allowed', sap_number, status, action }`: the message names the issuance, its status and the action in English, the fields next to it let the client say the same in Hebrew:

| From | assign | self pickup | delete | edit (priority, date, notes) | remove item | self pickup report (the handover) |
| --- | --- | --- | --- | --- | --- | --- |
| unassigned, assigned, not delivered | yes | yes | yes | yes | yes | no |
| self pickup | yes | no | yes | yes | yes | yes |
| delivered | no | no | no | no | no | no |
| partially delivered | no | no | no | no | no | no |
| deleted | no | no | no | no | no | no |

**Self pickup handover.** A `self_pickup` issuance shows no courier: its open task was cancelled when it moved there, and whatever closed task it still has is history, not current (`current_task` is null, the courier sort key too). The warehouse manager completes it with `POST /issuances/:id/self-pickup/report`, the courier's report body checked by the same validators. Under the issuance lock the service writes a done task with no courier (`courier_id` null, `assigned_by` the manager; the courier board filters by `courier_id`, so no courier ever sees it), the attempt with its item answers, recipient and signature, then the issuance: the status is the outcome of the answers exactly as after a courier report, `self_pickup` stays true, `revision` moves, and `delivered_by_user_id` records the manager from the token (never from the body). The board and the detail show that manager's display name where the courier would be. A manager has no `couriers` row: managers never appear in the assign dialog or the couriers page. The row allows the report from `self_pickup` only, so a second report meets the status the first one set and gets the 409. The answers are validated outside the lock against the lines loaded then, so under the lock the service also checks that `revision` is still the one it loaded: a line another manager removed meanwhile is a 409 `revision_changed` (`sap_number` in the body, worded in Hebrew by the dialog, which reloads), not an attempt on a line that is gone. A courier assignment and a second move to self pickup clear `delivered_by_user_id`: the record names the manager only while the handover is the last delivery of the issuance; the handover task itself stays in the task history.

**Removing a line.** `DELETE /issuances/:id/items/:itemId` takes one SAP line off the document, from the statuses of the edit row (the same table column; both that and the next rule are assumptions, README open decision 14). Under the issuance lock the line gets `removed_at`, `revision` moves by one and nothing else changes: no status, no task cancelled, no attempt touched; a courier who refreshes sees one line less, a report signed against the old line set meets `revision_changed`, a legacy report (no revision) or a handover whose validation a removal raced meets it under the lock too (see [What invalidates a report](offline-sync.md#what-invalidates-a-report)), and the manager's review of such a conflict still names the removed line (`GET /conflicts/:id` lists the lines with `removed_at`). The last live line is refused with 409 `last_item`: the report validator rejects an issuance with no lines, so an empty issuance could never be delivered, and the manager deletes the issuance instead; nothing is deleted on its own. A line that is not live on that issuance is a 404, so repeating the call writes nothing.

Bulk assignment is all or nothing: one closed issuance in the selection fails the whole batch and nothing is written. Mark urgent skips closed rows and reports how many changed.

**Delivery report validation** (`server/src/delivery/attempt.validation.ts`): exactly one answer per item, no unknown or duplicate item ids, `delivered` must be a real boolean, a reason from the closed list plus details up to 100 characters only on a line that was not delivered, another recipient needs name, numeric id and phone, the signature must be a real PNG (magic bytes checked) up to 1 MB. The recipient and the signature are required only when at least one line was delivered: a report whose every line is "not delivered" has no one to sign, so both may be left out and are stored as null (sent anyway, by an older build, they are checked and stored as before). The outcome is derived from the validated answers, never taken from the body. The JSON body is capped at 2 MB.

**Concurrency.** Every change to an issuance or its tasks locks the issuance row first (`SELECT ... FOR UPDATE`), always in the same order: issuance, then task. Two reports on the same task, or a report racing a reassignment, run one after the other and the second gets a 409. Closing a task is a conditional update on `status = pending` inside the same transaction, so nothing closes twice even without the lock. Related status changes are written together or not at all. The `xml_outbox` row of a status change is inserted last, after the audit row, on the same transaction and without a lock of its own: it commits or rolls back with the change, and the lock order stays issuance, then task. Its `sequence` is the issuance's row count plus one, safe because every writer holds the issuance lock. The export worker claims rows with one `UPDATE ... FOR UPDATE SKIP LOCKED` statement (two processes never take the same row, a row is not taken while an earlier sequence of its issuance is pending or processing) and uploads outside any transaction, see [XML export](xml-export.md#lifecycle-of-a-row).

**Idempotent delivery reports.** A report that carries an `operation_id` (every report the tablet sends, see below) is looked up under the same locks before anything else: a stored operation of the same account with the same task and the same payload hash returns the stored result with `replayed: true`, even when the task closed meanwhile (that is the "commit succeeded, response lost" case). The same id with a different task or content is a 409 `operation_reused`. The lookup is scoped by the account (`user.sub`), so another account using the same id never sees the first account's result or signature. The receipt row is written in the same transaction as the attempt and the status changes; a rejected report leaves no row. A unique index on `(user_id, operation_id)` backs this up: a second identical request that gets past the lock hits the index, and the service answers it with the row the first request committed. Requests without an operation id behave exactly as before.

**Audit log.** Every state change writes one `audit_log` row inside its own transaction, explicitly in the service that performs it (no interceptor, no request id middleware), and only when something changed: a PATCH that repeats the stored values, a replayed delivery report, a second mark urgent on rows already urgent or a repeated review with the same note write nothing. Rejected requests (400, 403, 404, 409) write nothing either; there is no exception any more: `auth.login_failed` was the one (a wrong password) and is not written since the mock login replaced the password (an unknown identity is a 400, a missing `users` row a 503, neither leaves a row); the value stays in the enum for the rows already stored. The transition table, the offline conflict rules, the response bodies and the status codes are untouched: `mark-urgent` still answers with the count of editable rows and writes rows only for the ones whose priority moved. The actions:

| Action | Entity | `details` |
| --- | --- | --- |
| `issuance.assign` | issuance | `courier_id`, `task_id`, `scheduled_date`, `from_status`; one `batch_id` per request |
| `issuance.edit` | issuance | `changes` over `priority`, `delivery_date`, `notes`, each as `{ from, to }` |
| `issuance.self_pickup` | issuance | `from_status`, plus `changes` when field edits came along |
| `issuance.self_pickup_report` | issuance | `task_id`, `attempt_id`, `outcome`, `items_delivered`, `items_total`, `revision` (the issuance revision after the handover); the actor is the manager who handed over |
| `issuance.mark_urgent` | issuance | `from_priority`; one `batch_id` per request |
| `issuance.remove_item` | issuance | `item_id`, `line_no`, `product_name`, `items_left`, `revision` (the issuance revision after the removal) |
| `issuance.delete` | issuance | `reason`, `from_status` |
| `courier.create`, `courier.reactivate` | courier | `name`, `employee_id` |
| `courier.update` | courier | `changes` over `name`, `employee_id`, `id_number`, `phone`, `email`, `zones` |
| `courier.remove` | courier | `name`; one `batch_id` per request |
| `delivery.report` | delivery_task (`issuance_id` set) | `task_id`, `attempt_id`, `outcome`, `operation_id`, `items_delivered`, `items_total`, `revision` (the issuance revision after the report); the actor is the courier's account |
| `delivery.conflict_record` | delivery_conflict (`issuance_id` set) | `task_id`, `operation_id`, `rejection_code`, `submitted_revision` |
| `delivery.conflict_review` | delivery_conflict (`issuance_id` set) | `review_version` |
| `auth.login` | user | none |
| `auth.login_failed` | not written any more (the mock login has no credential to get wrong, see [Authentication](auth.md)); the rows already stored carry `known_user` and, for an existing account, `username` | |
| `system.seed` | system (`actor_type = system`) | `users`, `couriers`, `issuances` |

The existing `Logger` lines stay as operator output; the table is the record. A manager reads it through `GET /api/audit` ([API](api.md)).

## Schema upgrade

Migrations arrived with the offline work and stay minimal: one hand written class per schema change under `server/src/migrations/`, a `DataSource` for the TypeORM CLI in `server/src/data-source.ts` (same `.env` and connection options as the app, `synchronize` always off there), and four scripts in `server/package.json`:

| Script | What |
| --- | --- |
| `npm run migration:run` | applies the pending migrations from the TypeScript sources (ts-node) |
| `npm run migration:run:prod` | the same from `dist/` (`npm run build` first), for a box without devDependencies |
| `npm run migration:revert` | reverts the last applied migration |
| `npm run migration:show` | lists the migrations and marks the applied ones |

Run `migration:run` (or `migration:run:prod`) before starting a new server build everywhere except a LOCAL machine with `DB_SYNCHRONIZE=true`, where `synchronize` adds the same objects on start and the migration becomes a no-op. The application never runs migrations by itself (no `migrationsRun`): a schema change is a deliberate step, not a side effect of a restart. TypeORM keeps the applied list in a `migrations` table it creates on the first run.

`server/src/e2e/migrations.e2e.spec.ts` is the harness: on a database of its own (`<DB_NAME_TEST>_migrations`) it builds the current schema from the entities (the base tables have no migration), puts `users` back in its previous shape with the last migration's `down`, inserts a row the way an upgraded database holds one, runs the migrations as `migration:run` does and asserts that the row survived, that nothing is left for `synchronize` to change (the schema builder's pending SQL is empty, so migrations and entities agree), that a second run is a no-op, and that `down` takes the step back with the rows. A new migration is covered by it only for the parity check; one that changes data needs its own case there (`CourierUserUnique` has one: the refusal with duplicates, the constraint once they are fixed).

Ten migrations so far, all guarded by `IF NOT EXISTS` / `IF EXISTS` and reversed in `down`, the first seven adding objects only (nothing is wiped, the tables of the previous version are assumed to exist), all with column types and constraint names that match what `synchronize` generates from the entities, so a LOCAL database that ran either path shows no diff to the other:

- `OfflineSync1790600000000`: `issuances.revision`, `delivery_attempts.client_reported_at` and the `delivery_operations` table with its unique index.
- `ConflictEvidence1790800000000`: the `delivery_conflicts` table with its unique index on (`user_id`, `operation_id`) and the foreign key to `delivery_tasks`. The constraint names come from TypeORM's own naming strategy inside the migration.
- `NoRecipientWithoutDelivery1790900000000`: `delivery_attempts.recipient_type`, `delivery_conflicts.recipient_type` and `delivery_conflicts.signature_png` become nullable, for a report whose every line is "not delivered" (no one received, no one signed). `DROP NOT NULL` is a no-op where `synchronize` already did it. The revert puts the constraints back and is refused by PostgreSQL while such rows exist.
- `AuditLog1791000000000`: the `audit_log` table with its four indexes on (`issuance_id`, `at`), (`actor_user_id`, `at`), (`entity_type`, `entity_id`, `at`) and (`at`). No foreign keys by design; the primary key and the index names come from TypeORM's naming strategy inside the migration, like `ConflictEvidence`.
- `SelfPickupHandover1791100000000`: `issuances.delivered_by_user_id` (nullable integer, no foreign key, like `delivery_tasks.assigned_by`) and `delivery_tasks.courier_id` becomes nullable for the handover task. The revert puts `NOT NULL` back and is refused by PostgreSQL while handover tasks exist.
- `RemoveIssuanceItem1791200000000`: `issuance_items.removed_at` (nullable `timestamptz`, the TypeORM delete date column of a line the manager took off). The revert drops the column, which brings every removed line back as a live one: the mark was the only thing that hid them.
- `XmlOutbox1791300000000`: the `xml_outbox` table with its uuid primary key (`DEFAULT gen_random_uuid()`, built into PostgreSQL 13+, no extension) and its three indexes on (`status`, `next_retry_at`), (`issuance_id`, `sequence`) unique and (`status`, `lease_until`). No foreign keys by design; the names come from TypeORM's naming strategy inside the migration, like `AuditLog`. The revert drops the table and with it every row not yet exported.
- `AuthMockIdentities1791400000000`: `users.password_hash` dropped (the mock login has no credential, [docs/auth.md](auth.md)) and `users.email` added (nullable `varchar`, what the identity provider says about the person). The revert drops `email` and puts `password_hash` back as `NOT NULL DEFAULT ''`: the hashes are gone for good, every row gets an empty value nothing verifies against. The only migration that removes a column; the rows survive both ways.
- `CourierUserUnique1791500000000`: a unique constraint on `couriers.user_id` (one login account holds one courier row at most; null stays repeatable), named by TypeORM's strategy like the entity's `unique: true`. It reads the data first: a database with two rows for one account is refused with the list, nothing is forced over them. The revert drops the constraint.
- `XmlImportFiles1791600000000`: the `xml_import_files` table of the import ETL with its uuid primary key (`DEFAULT gen_random_uuid()`) and its two unique constraints on `content_sha256` and `document_id`. No foreign keys by design; the names come from TypeORM's naming strategy inside the migration, like `XmlOutbox`. Adds objects only; the revert drops the table and with it the record of which documents were imported (the issuances stay).
