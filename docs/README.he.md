# מערכת ניפוק ציוד דיגיטלית

> The English README at the repository root is the entry point. This file keeps the original Hebrew product specification and the notes written while the foundation was built.

מסמך אפיון ראשוני למערכת Web לניהול ניפוק ומסירת ציוד. המערכת מחליפה תהליך ידני בנייר: מקבלת בקשות או משלוחים מ-SAP, מאפשרת למנהל להקצות אותם לשליחים, מתעדת מסירה וחתימת מקבל, ומחזירה סטטוס ל-SAP.

> המסמך מבוסס על האפיון שסופק. זהו אפיון מוצר, ולא תיעוד של מערכת שכבר מומשה. סעיף "החלטות פתוחות" מרכז פרטים שחסרים לפני פיתוח.

## מטרות

- מעקב בזמן אמת אחר בקשות ניפוק, משלוחים ומצב הביצוע.
- זיהוי מהיר של פרטי הציוד או הבקשה באמצעות QR, עם אפשרות להזנה ידנית.
- תיעוד זהות השליח והמקבל, מועד המסירה, חתימה ואסמכתאות.
- סנכרון נתוני הבקשה והסטטוסים עם SAP.
- צפייה בהיסטוריה, הפקת אישורים ודוחות ביצוע.

## משתמשים והרשאות

| תפקיד | פעולות עיקריות |
| --- | --- |
| מנהל מערכת | כניסה וניהול משתמשים ושליחים, הקצאת משלוחים, מעקב ודוחות |
| שליח / מנפק | צפייה במשימות שהוקצו לו, סריקת QR או הזנה ידנית, מסירה ותיעוד חתימה |
| מנהל לוגיסטיקה | צפייה בהיסטוריה, ניתוח נתונים ודוחות, בהתאם להרשאות שיוגדרו |
| SAP | מערכת חיצונית המחליפה נתוני בקשות, משלוחים וסטטוסים דרך ממשק אינטגרציה |

## תהליך העבודה המרכזי

1. SAP מעביר בקשת ניפוק או משלוח למערכת.
2. המערכת מקשרת לבקשה פרטי ציוד ומזהה QR מתאים.
3. המנהל מקצה את המשלוח לשליח, והשליח מקבל עדכון על משימה חדשה.
4. השליח מגיע ליעד וסורק QR. אם הסריקה אינה אפשרית, הוא מזין פרטים ידנית.
5. המערכת מציגה את פרטי הציוד, הבקשה והמשלוח לבדיקה.
6. המקבל מאשר את המסירה בחתימה דיגיטלית. ניתן לתעד תמונות או אסמכתאות והערות.
7. המערכת שומרת את אירוע הניפוק, מעדכנת סטטוס ושולחת את הנתונים הנדרשים ל-SAP.
8. ניתן להפיק אישור PDF, לשלוח אישור ב-SMS או בדוא"ל ולצפות בפעולה בהיסטוריה.

## מסכים ויכולות

### דשבורד (`/`)

- תמונת מצב של ניפוקים פעילים, ממתינים והושלמו.
- התראות ואירועים דחופים, סטטיסטיקות ומדדי ביצוע.
- תצוגה בהתאם לתפקיד המשתמש ועדכון נתונים בזמן אמת.

### סריקת QR (`/scan`)

- שימוש במצלמת המכשיר לסריקה וזיהוי פרטי הבקשה או הציוד.
- הצגת נתוני הפריט או המשלוח לאחר זיהוי, לצד טיפול בסריקה שגויה.
- מעבר להזנה ידנית ושמירת תיעוד סריקות לצורכי בקרה.

### הזנה ידנית (`/manual-entry`)

- הזנת מזהה ציוד, פרטי מקבל, תאריך, כמות והערות, לפי הנתונים הזמינים.
- שדות חובה, בדיקות תקינות והשלמת פרטים מתוך SAP ככל שהממשק מאפשר.
- שמירת טיוטה והצגת אישור לפני השלמת הניפוק.

### פרטי ניפוק (`/issuanceDetail`)

- הצגת פרטי ניפוק, ציוד, שליח, יעד, תאריך וסטטוס.
- חתימת מקבל על מסך מגע, שמירת תמונות ואסמכתאות, ועדכון סטטוס.
- הצגת היסטוריית שינויים, הפקת אישור PDF ושליחת אישור בדוא"ל או ב-SMS.
- העברת העדכון ל-SAP לאחר השלמת הניפוק.

### היסטוריה (`/history`)

- רשימת ניפוקים עם מיון, סינון וחיפוש לפי מזהה, שליח, סטטוס ותקופה.
- דפדוף בין עמודים, צפייה בפרטי רשומה וייצוא CSV או Excel.
- סינון המידע בהתאם להרשאות המשתמש.

### אנליטיקה (`/analytics`)

- מדדים וגרפים לפי תקופה, שליח וציוד.
- נתוני השלמה, זמני טיפול ומגמות לאורך זמן.
- ייצוא דוחות PDF או Excel בהתאם להרשאות.

### ניהול (`/admin/*`)

- כניסת מנהל עם אימות, ניהול סשן וניסיון כניסה מוגבל.
- יצירה וניהול שליחים, שדות זיהוי ופרטי קשר, אזורי עבודה וייבוא CSV או Excel.
- צפייה במשלוחים הממתינים להקצאה, הקצאה לשליח או לכמה שליחים בהתאם לחוקי העסק, ועדכון השליח.
- מעקב אחר הקצאות וסטטוסי משלוחים.

## מודל נתונים ראשוני

| `Courier` | `id`, `name`, `employeeId`, `phone`, `email`, `zones` | משלוחים וניפוקים |
| `Shipment` | `id`, `origin`, `destination`, `priority`, `assignedAt` | שליח וניפוקים |

המודל הוא נקודת פתיחה בלבד. שדות מזהי SAP, הקשר בין בקשה, משלוח ופריט, ריבוי פריטים במשלוח, והרשאות בין משתמש לשליח מחייבים אישור מול הגורמים העסקיים.

חתימה תישמר כתמונה בפורמט מוגדר, לצד מזהה הניפוק וחותמת זמן, עם גישה מוגבלת לאחסון.

## אינטגרציות

- **SAP:** קבלת בקשות ומשלוחים, שיוך נתונים מזהים, ודיווח על מסירה וסטטוס. יש להגדיר ממשק, מיפוי שדות, כיוון התעבורה, אימות, טיפול בשגיאות וניסיונות חוזרים.
- **מצלמה:** סריקת QR דרך מכשיר השליח.
- **אחסון קבצים:** חתימות, תמונות ואסמכתאות בהרשאות מתאימות.
- **הודעות:** עדכון שליח ואישור מסירה דרך SMS או דוא"ל, בהתאם לשירותים שייבחרו.
- **מסמכים:** יצירת אישור מסירה ב-PDF וייצוא נתונים ל-CSV או Excel.

## דרישות ממשק ומגבלות

- ממשק בעברית בכיוון RTL, כולל שימוש נוח בטלפון לשליחים ובמחשב למנהלים.
- תמיכה בדפדפנים מודרניים ובמכשירי iOS ו-Android.
- אין באפיון תמיכה בעבודה ללא חיבור לרשת. פעולות מסירה מחייבות תקשורת זמינה. (כך באפיון המקורי. תמיכה בעבודה ללא רשת בצד המשנע נוספה מאוחר יותר, ראו "עבודה ללא רשת" בחלק "הפרויקט בפועל" למטה.)
- יש לוודא הרשאות לצפייה ולשינוי מידע, תיעוד אירועים ושמירה מאובטחת של חתימות וקבצים.
- מדדי זמן תגובה, עומסים, זמינות ומשך שמירת מידע טרם הוגדרו.

## סדר מימוש מוצע

1. **תשתית ותהליך בסיסי:** חיבור ל-SAP, ניהול זהויות ומשלוחים, הקצאה, QR ומסך ניפוק.
2. **ביצוע מסירה:** הזנה ידנית, חתימה, אסמכתאות, עדכון סטטוס, היסטוריה ואישור מסירה.
3. **ניהול ודיווח:** דשבורד עשיר, אנליטיקה, ייצוא דוחות ושיפורי תפעול.

חלוקה זו היא הצעה לתכנון, ולא לוח זמנים שאושר.

## החלטות פתוחות לפני פיתוח

1. מהו אובייקט המקור ב-SAP: בקשת ניפוק, הזמנה, משלוח או פריט ציוד? איזה מזהה מופיע ב-QR ומי יוצר אותו?
2. האם משלוח כולל כמה פריטים וכמה מקבלים? האם מותרת מסירה חלקית או כמה ניסיונות מסירה?
3. מהם הסטטוסים, חוקי המעבר ביניהם, ומתי ניפוק נחשב סופי?
4. מהו הממשק המוסכם עם SAP, ומה קורה כששמירה מקומית מצליחה אך עדכון SAP נכשל?
5. מי רשאי לראות חתימות, תמונות ופרטים אישיים, ולכמה זמן יש לשמור אותם?
6. האם נדרש אימות זהות של המקבל מעבר לחתימה, ומה נחשב ראיה קבילה למסירה?
7. האם קיימת חובה עסקית לעבודה ללא רשת? האפיון הנוכחי אינו כולל תמיכה בכך. (נענה בינתיים: עבודה ללא רשת בצד המשנע מומשה, ראו "עבודה ללא רשת" למטה. צד המנהל נשאר מקוון בלבד.)
8. אילו ערוצי התראה וייצוא נדרשים כבר בגרסה הראשונה?

## קריטריוני קבלה ראשוניים

- מנהל יכול להקצות משלוח שהתקבל לשליח, והשליח רואה אותו ברשימת המשימות שלו.
- סריקת QR תקין פותחת את הפרטים המתאימים; QR לא מוכר מציג שגיאה ברורה ומאפשר הזנה ידנית.
- לא ניתן להשלים מסירה ללא שדות החובה ואישור המקבל לפי הכללים שיוגדרו.
- אירוע שהושלם נשמר עם זמן, שליח, מזהים, סטטוס וחתימה, ומופיע בהיסטוריה למשתמש מורשה.
- השלמת מסירה מעדכנת את SAP או מציגה ומאפשרת טיפול בכשל סנכרון, בלי לאבד את האירוע.

# הפרויקט בפועל: בסיס להרצה מקומית

הריפו מכיל עכשיו יישום שרץ מקומית ומכסה את הזרימה המרכזית: מנהל מחסן משייך הנפקות לשליחים בדסקטופ, ושליח מדווח מסירה עם חתימה מטאבלט, גם בלי חיבור לרשת (ראו "עבודה ללא רשת"). המסכים עוקבים אחרי העיצוב בתיקיית `design/` (יצוא PNG מפיגמה, לא נכנס ל-git), ולא אחרי הניסוחים הישנים באפיון שלמעלה. איפה שהעיצוב וה-README חלוקים, העיצוב קובע: "הנפקה" ולא "ניפוק", "משנע" ולא "שליח".

## מבנה

| תיקייה | מה יש בה |
| --- | --- |
| `client/` | React 18 + TypeScript + Vite. MUI 5 עם RTL, SCSS, react-router, i18next. `idb` ל-IndexedDB, `vite-plugin-pwa` ל-service worker, vitest לבדיקות. |
| `client/src/courier/offline/` | שכבת הנתונים המקומית של המשנע: מבנה ה-IndexedDB, קריאות וכתיבות, ה-worker של הסנכרון, ה-hooks, וקבצי הבדיקה. |
| `server/` | NestJS 10 + TypeORM + PostgreSQL. `src/migrations/` ו-`src/data-source.ts` ל-migrations. |
| `shared/` | enums וממשקים (`@core.ts`), עזרים (`@utils.ts`) ומילון העברית (`i18n/he.ts`). משותף לשני הצדדים. |
| `design/` | יצוא המסכים מפיגמה ודיאגרמת ארכיטקטורת המידע. ב-`.gitignore`. |
| `docker-compose.yml` | PostgreSQL 16 על פורט 5433 (5432 היה תפוס במכונה שבה זה נבנה). |

## הרצה

דרישות: Node 20, Docker Desktop.

```bash
docker compose up -d
```

```bash
cd server && npm install && cp .env.example .env && npm run seed && npm run start:dev
```

```bash
cd client && npm install && npm run dev
```

הלקוח ב-http://localhost:5173 ומפנה `/api` לשרת ב-3000. לשרת הפיתוח אין service worker (הוא נרשם רק בגרסה הבנויה), אז שכבת הנתונים המקומית והסנכרון עובדים בו כרגיל, אבל טעינה מחדש בלי רשת לא. לזה משתמשים בגרסה הבנויה, ראו "HTTPS ובדיקת הגרסה הבנויה". `npm run seed` מוחק את כל הטבלאות ומכניס את נתוני הדוגמה מחדש, אפשר להריץ אותו בכל פעם שרוצים להתחיל נקי. במכונה מקומית הסכמה נבנית מה-entities עם `synchronize` (`DB_SYNCHRONIZE=true`). בכל מקום אחר היא מתקדמת עם migrations, ראו "עדכון סכמה" בסעיף ההקשחה.

חשבונות פיתוח, כולם עם הסיסמה `1234`:

| משתמש | תפקיד | מה רואים |
| --- | --- | --- |
| `manager`, `manager2` | מנהל מחסן | לוח ניהול הנפקות, ניהול שליחים, דוחות |
| `courier1`, `courier2`, `courier3` | משנע | לוח משלוחים ופרטי הנפקה |

הרשימה מוצגת גם בעמוד הכניסה, כי השרת רץ ב-`AUTH_STRATEGY=dev-local`.

## אימות: פיתוח מול ייצור

מה שקיים הוא אימות פיתוח בלבד: שם משתמש וסיסמה מול טבלת `users` שנזרעה, ו-JWT ב-localStorage. הוא יושב ב-`server/src/auth` ומסומן ככזה בקוד. שיטת ההזדהות בייצור לא נקבעה (בדיאגרמה: "אימייל וסיסמא או הזדהות לאומית?"), ולכן לא נבנה כאן 2FA, הזדהות לאומית או SSO. כשתתקבל החלטה, החלק שמתחלף הוא הנפקת הטוקן ב-`auth.service.ts` ועמוד הכניסה. ה-guard, התפקידים והמסכים לא תלויים בזה.

## מודל הנתונים

לפני הסכמה, ההבחנה בין המושגים, כי האפיון והעיצוב משתמשים ב"הנפקה" לכמה דברים שונים:

- **הנפקה** (`issuances`): מסמך ה-SAP. מי הלקוח, לאן, מה העדיפות. קיים גם אם אף אחד עוד לא נשלח למסור אותו. הסטטוס שלו משקף את התוצאה האחרונה. העמודה `revision` היא אסימון המקביליות של דיווח שנכתב בלי רשת, ראו "מה מבטל דוח".
- **פריט בהנפקה** (`issuance_items`): שורת מוצר במסמך, עם מק"ט, מספר תחנה וסריאלי. השליח עונה "נמסר / לא נמסר" לכל פריט בנפרד, ומכאן מסירה חלקית.
- **משימת מסירה** (`delivery_tasks`): "לך תמסור הנפקה X", שיוך של הנפקה אחת לשליח אחד לתאריך. זה מה שלוח המשלוחים של השליח מציג. שינוי שליח מבטל את המשימה הישנה ופותח חדשה, כך שההיסטוריה של מי החזיק את זה נשמרת.
- **שליח / משנע** (`couriers`): מי שמוביל בפועל. נפרד מ-`users`: שליח קיים במערכת גם בלי חשבון כניסה (שתי חברות חיצוניות בנתוני הדוגמה).
- **ניסיון מסירה** (`delivery_attempts` + `delivery_attempt_items`): מה שהשליח דיווח בדלת: תוצאה לכל פריט עם סיבת אי מסירה, ומי קיבל והחתימה כשלפחות פריט אחד נמסר. בניסיון `not_delivered` ארבע עמודות המקבל והחתימה הן null: אף אחד לא קיבל ואף אחד לא חתם, אז המסך לא שאל. היום ניסיון אחד סוגר משימה. אם יוגדר "ניסיון חוזר מחר", הטבלה כבר מוכנה לכמה ניסיונות על אותה משימה. `reported_at` הוא זמן הקליטה בשרת; `client_reported_at` הוא שעון המכשיר ברגע הלחיצה על שליחה, נשמר בנפרד כי אי אפשר לסמוך עליו והוא יכול להיות שעות לפני הקליטה אחרי ניתוק.
- **פעולת דיווח** (`delivery_operations`): הקבלה על דוח שנשלח עם מזהה פעולה: החשבון, המשימה, הניסיון שנוצר, hash של הדוח אחרי ולידציה, וגוף התשובה המדויק שהוחזר. אותו מזהה מאותו חשבון מקבל את התשובה השמורה במקום ניסיון שני. רק דוח שהתקבל מקבל שורה, והיא נכתבת באותה טרנזקציה עם הניסיון.
- **דוח שנדחה** (`delivery_conflicts`): דוח שנתיב הדיווח סירב לו ב-409 והטאבלט מסר כראיה: החשבון והמשנע (מהטוקן), המשימה וההנפקה המקוריות, ה-revision שהדוח נכתב מולו, התשובות, המקבל והחתימה (null כשהדוח שנחתם לא מסר דבר, אותו כלל כמו בניסיון מסירה), זמן המכשיר, hash של התוכן, קוד הדחייה והמצב בשרת ברגע הרישום (`observed`). שדות הבדיקה (`review_status`, `reviewed_by`, `reviewed_at`, `review_note`, `review_version`) הם הרישום של המנהל ויושבים בנפרד מהתוכן שנמסר, שלא משתנה לעולם. שום דבר כאן הוא לא מסירה: אין ניסיון, אין סגירת משימה, אין סטטוס להנפקה ואין קידום revision. ייחודי לכל (חשבון, מזהה פעולה).

סטטוסי הנפקה: `unassigned` (לא שובץ), `assigned` (שובץ למשנע, ואצל השליח: ממתין), `delivered`, `partially_delivered`, `not_delivered`, `self_pickup`, `deleted`. מחיקה היא soft delete עם סיבה, כמו שהעיצוב מבקש.

## הנחות עבודה שלא נסגרו

רשומות כאן במקום להיות קבורות בקוד. הארכיטקטורה לא ננעלה עליהן:

1. הנפקה שלא נמסרה חוזרת ללוח המנהל עם הסטטוס, והמנהל מחליט אם לשייך מחדש. לא נבנה ניסיון חוזר אוטומטי.
2. איסוף עצמי סוגר את הצד של השליח. מה SAP צריך לשמוע על זה לא ידוע.
3. קיבוץ "2 הנפקות" לאותו לקוח וכתובת הוא תצוגה בלבד. אין ישות קבוצה ב-DB.
4. אות הקידומת במספר ההנפקה (ס' / ד' / כ') נשמרת בעמודה נפרדת ולא מפורשת. אף אחד לא הסביר מה היא.
5. החתימה נשמרת כ-PNG בתוך ה-DB. האפיון מבקש אחסון קבצים מוגבל הרשאות, זה שלב הבא.
6. שליח אחד להנפקה. "הקצאה לכמה שליחים" מהאפיון לא עוצבה.
7. ממשק SAP לא הוגדר ולא הומצא. עמודת `source` בהנפקה מסמנת מאיפה היא הגיעה (`sample` לנתוני הדוגמה), וזה המקום היחיד שנוגע בזה.
8. סדר המשימות של השליח הוא לפי עדיפות ותאריך. ידית הגרירה בכרטיס היא ויזואלית בלבד.
9. הנפקה שנמסרה חלקית קפואה: אי אפשר לשייך אותה מחדש, למחוק או להעביר לאיסוף עצמי עד שיוחלט מה קורה עם הפריטים שכבר נמסרו. ראו "החלטה שנדרשת" בסעיף ההקשחה.
10. דוח שהשרת דחה בסנכרון נשאר במכשיר של המשנע, והמשנע מציג אותו למנהל. מסך מנהל לדוחות כאלה, או העלאה של הדוח השמור לבדיקה, לא עוצבו. ראו "דוחות שלא נקלטו".

## מה משתמש בנתוני דוגמה או עדיין לא ממומש

- כל ההנפקות, השליחים והלקוחות מגיעים מ-`server/src/seed/seed.data.ts`. אין SAP.
- סריקת QR ממומשת בשני הלוחות באמצעות qr-scanner. הקוד מכיל את מספר ההנפקה ב-SAP בספרות בלבד, כולל אפסים מובילים, ללא קישור או JSON. נדרשים HTTPS או localhost והרשאת מצלמה. החיפוש אצל השליח מתחיל במכשיר, והמנהל פותח את ההנפקה בהתאמה מדויקת. הזנה ידנית זמינה גם כשהמצלמה אינה זמינה.
- ניהול שליחים: רשימה בלבד. יצירה, עריכה וייבוא מאקסל בלי עיצוב.
- דוחות ודאשבורד KPI: עמוד placeholder. בדיאגרמה יש סימן שאלה על ההגדרה.
- היסטוריה, אנליטיקה, PDF, SMS ודוא"ל: לא נבנו. אין להם מסך בעיצוב.
- כפתור "איתור הנפקה" בצד המנהל פותח סריקה והזנה ידנית, ללא תלות במסנני הלוח.
- עבודה ללא רשת קיימת בצד המשנע בלבד. אין סנכרון כשהאפליקציה סגורה (בלי Background Sync). דוח שנדחה מגיע למנהל כראיה בלבד: הוא יכול לקרוא אותו ולסמן שנבדק, לא להחיל, למזג או לשייך מחדש דרכו. לאייקון ה-PWA יש SVG בלבד, בלי PNG ובלי אייקון למסך הבית של iOS.

## API

כל הנתיבים תחת `/api`, דורשים `Authorization: Bearer <token>` חוץ מהכניסה.

| נתיב | תפקיד | מה |
| --- | --- | --- |
| `POST /auth/login`, `GET /auth/me`, `GET /auth/dev-accounts` | | כניסת פיתוח; אובייקט המשתמש מחזיר `id` לצד ה-`sub` של ה-JWT |
| `GET /issuances`, `GET /issuances/:id`, `GET /issuances/summary` | מנהל | לוח, פרטים, ווידג'ט ערים |
| `PATCH /issuances/:id` | מנהל | עדיפות, מועד חלוקה, איסוף עצמי |
| `POST /issuances/assign`, `POST /issuances/mark-urgent` | מנהל | פעולות על כמה הנפקות |
| `DELETE /issuances/:id` | מנהל | מחיקה רכה עם סיבה |
| `GET /couriers` | מנהל | שליחים עם עומס |
| `GET /delivery/tasks`, `GET /delivery/tasks/:id` | משנע | המשימות שלי |
| `POST /delivery/tasks/:id/conflicts` | משנע | דוח שנתיב הדיווח סירב לו ב-409, נשמר כראיה; אותו גוף עם `operation_id` חובה; עונה `IConflictReceipt`, או את תוצאת המסירה כשהפעולה ההיא כבר הוחלה |
| `GET /delivery/conflicts?operation_ids=` | משנע | סטטוס הבדיקה של הראיות של הקורא בלבד (`IConflictStatus[]`) |
| `GET /conflicts`, `GET /conflicts/:id` | מנהל | דוחות שנדחו (`?status=pending|reviewed|all&page=&page_size=`, בלי חתימות ברשימה), דוח אחד עם החתימה לצד המצב הנוכחי |
| `POST /conflicts/:id/review` | מנהל | `{ note, version }`: סימון כנבדק; 409 `review_conflict` עם הבדיקה הקיימת כשמנהל אחר הקדים |
| `POST /delivery/tasks/:id/attempts` | משנע | דיווח מסירה (`IAttemptPayload`), אופציונלית עם `operation_id`, `issuance_revision`, `client_reported_at`; מחזיר `IAttemptResult` |
| `GET /delivery/lookup?number=` | משנע | איתור לפי מספר הנפקה |

### שינויים בחוזה ה-API

נעשו בשביל העבודה ללא רשת, ב-`shared/@core.ts`:

- `POST /delivery/tasks/:id/attempts` מקבל שלושה שדות אופציונליים. `operation_id`: 8 עד 64 תווים של אותיות, ספרות, `_` או `-`, אחרת 400; איתו הבקשה אידמפוטנטית כמתואר ב"דיווחים אידמפוטנטיים" בסעיף ההקשחה. `issuance_revision`: מספר שלם, אחרת 400; כשהוא קיים הוא חייב להיות שווה ל-`issuances.revision` הנוכחי, אחרת 409 עם `revision_changed`. `client_reported_at`: מחרוזת ISO 8601 מדויקת, נשמרת על הניסיון כ-`client_reported_at`; כל דבר אחר נשמר כ-null ולא מחזיר 400.
- גוף ההצלחה הוא `IAttemptResult`: `{ attempt_id, outcome, task_id, reported_at, operation_id? }`, הרחבה של `{ attempt_id, outcome }` הישן, עדיין 201. שליחה חוזרת של פעולה שכבר נשמרה מחזירה את הגוף השמור עם `replayed: true`.
- כל 409 בנתיב הזה הוא `{ statusCode: 409, message, code }` כש-`code` מ-`ReportConflictCode` (`task_closed`, `task_cancelled`, `issuance_not_assigned`, `revision_changed`, `operation_reused`). שדה ה-`error` של Nest נעלם מהגופים האלה; `message` ו-`statusCode` נשארים. בקשה ישנה בלי מזהה פעולה עדיין מחזירה 409 עם ההודעה `task already closed`, עכשיו עם `code: task_closed`.
- `POST /auth/login` מחזיר `user: { id, sub, username, display_name, role, courier_id }` ו-`GET /auth/me` מחזיר `{ id, ...jwt payload }`: `id` הוא `users.id`, אותו ערך כמו `sub`, כדי שהלקוח לעולם לא ישמור נתונים מקומיים תחת מזהה לא מוגדר. הלקוח גם משלים `id` מ-`sub` לסשן שנשמר לפני השינוי.
- לטיפוסים המשותפים נוספו `IIssuance.revision`, `IDeliveryAttempt.client_reported_at` ו-`IDeliveryTask.local_report` (בצד הלקוח בלבד).

שום דבר אחר ב-API לא השתנה.

## הקשחת הזרימות

הזרימות של שיוך ודיווח מסירה נבדקות בצד השרת, בלי להסתמך על המסך.

**מעברי סטטוס.** הטבלה ב-`server/src/issuances/issuance.rules.ts` אומרת מאיזה סטטוס מותרת כל פעולה של המנהל. פעולה שלא ברשימה מחזירה 409 עם הודעה שמציינת את ההנפקה, הסטטוס והפעולה:

| מסטטוס | שיוך | איסוף עצמי | מחיקה | עריכה (עדיפות, מועד, הערות) |
| --- | --- | --- | --- | --- |
| לא שובץ, שובץ, לא נמסר | כן | כן | כן | כן |
| איסוף עצמי | כן | לא | כן | כן |
| נמסר | לא | לא | לא | לא |
| נמסר חלקית | לא | לא | לא | לא |
| נמחקה | לא | לא | לא | לא |

שיוך של כמה הנפקות הוא הכל או כלום: הנפקה אחת סגורה בבחירה מכשילה את כל הקבוצה ושום דבר לא נכתב. "סימון כדחוף" מדלג על שורות סגורות ומחזיר כמה עודכנו.

**החלטה שנדרשת.** מה עושים עם הנפקה שנמסרה חלקית? האפשרויות: משימה חדשה עם הפריטים שנותרו בלבד, השליח רואה את כל הפריטים כשהנמסרים מסומנים, או חזרה ל-SAP למסמך חדש. עד שתתקבל תשובה, ההנפקה קפואה והמנהל מקבל 409 כשהוא מנסה לשייך, למחוק או להעביר לאיסוף עצמי. המסך עדיין מציג את הכפתורים האלה, וההודעה מגיעה כ-toast באנגלית.

**ולידציה של דיווח מסירה.** ב-`server/src/delivery/attempt.validation.ts`: תשובה אחת בדיוק לכל פריט, בלי מזהים לא מוכרים או כפולים, `delivered` חייב להיות boolean אמיתי, סיבה מהרשימה הסגורה ופירוט עד 100 תווים רק בשורה שלא נמסרה, מקבל "אדם אחר" עם שם, ת.ז. בספרות וטלפון, חתימה כ-PNG אמיתי (בדיקת magic bytes) עד 1MB. המקבל והחתימה נדרשים רק כשלפחות שורה אחת נמסרה: בדוח שכל שורותיו "לא נמסר" אין מי שיחתום, אז אפשר להשמיט את שניהם והם נשמרים כ-null (אם נשלחו בכל זאת, מגרסה ישנה של הטאבלט, הם נבדקים ונשמרים כרגיל). התוצאה נגזרת מהתשובות שעברו ולידציה ולא מה-body. גודל ה-body מוגבל ל-2MB.

**מקביליות.** כל שינוי בהנפקה או במשימות שלה נועל קודם את שורת ההנפקה (`SELECT ... FOR UPDATE`), תמיד באותו סדר: הנפקה ואז משימה. כך שני דיווחים על אותה משימה, או דיווח מול שיוך מחדש, רצים אחד אחרי השני, והשני מקבל 409. סגירת המשימה היא update מותנה על `status = pending` בתוך אותה טרנזקציה, אז גם בלי הנעילה לא ייסגרו פעמיים. כל שינויי הסטטוס הקשורים נכתבים יחד או לא נכתבים.

**דיווחים אידמפוטנטיים.** דוח שמגיע עם `operation_id` (כל דוח שהטאבלט שולח) נבדק תחת אותן נעילות לפני כל דבר אחר: פעולה שמורה של אותו חשבון עם אותה משימה ואותו hash של התוכן מחזירה את התשובה השמורה עם `replayed: true`, גם אם המשימה נסגרה בינתיים (המקרה של "הכתיבה הצליחה, התשובה לא הגיעה"). אותו מזהה עם משימה או תוכן אחרים הוא 409 עם `operation_reused`. החיפוש מוגבל לחשבון (`user.sub`), אז חשבון אחר עם אותו מזהה לעולם לא מקבל את התשובה או את החתימה של הראשון. שורת הקבלה נכתבת באותה טרנזקציה עם הניסיון ושינויי הסטטוס; דוח שנדחה לא משאיר שורה. אינדקס ייחודי על `(user_id, operation_id)` מגבה את זה: בקשה זהה שנייה שעברה את הנעילה נתקלת באינדקס, והשירות עונה לה עם השורה שהראשונה כתבה. בקשה בלי מזהה פעולה מתנהגת בדיוק כמו קודם.

**מתגי פיתוח.** `server/src/env.ts` מרכז את ההחלטה "האם זה מחשב של מפתח". `ENVIRONMENT=LOCAL` הוא opt-in מפורש, ובלעדיו (או עם `NODE_ENV=production`):

- השרת מסרב לעלות כשה-`JWT_SECRET` חסר או עדיין ברירת המחדל.
- השרת מסרב לעלות עם `AUTH_STRATEGY=dev-local`, אלא אם `ALLOW_DEV_AUTH=true` הוגדר במפורש למכונת בדיקות בלי ספק זהות, ואז זה נרשם בלוג.
- `/api/auth/dev-accounts` מחזיר רשימה ריקה תמיד, גם עם `ALLOW_DEV_AUTH`.
- `npm run seed` מסרב לרוץ. גם ב-LOCAL הוא דורש `ALLOW_DESTRUCTIVE_SEED=true`.
- `synchronize` של TypeORM כבוי. גם ב-LOCAL הוא דורש `DB_SYNCHRONIZE=true`.
- הסכמה מתקדמת עם `npm run migration:run` (או `migration:run:prod`) לפני שמעלים build חדש. ב-LOCAL עם `synchronize` זה no-op.

**עדכון סכמה.** ה-migrations הגיעו עם העבודה ללא רשת ונשארו מינימליים: מחלקה אחת כתובה ביד לכל שינוי סכמה תחת `server/src/migrations/`, `DataSource` ל-CLI של TypeORM ב-`server/src/data-source.ts` (אותו `.env` ואותם פרטי חיבור כמו האפליקציה, `synchronize` תמיד כבוי שם), וארבעה סקריפטים ב-`server/package.json`: `migration:run` (מהמקורות, ts-node), `migration:run:prod` (מ-`dist/`, אחרי `npm run build`, למכונה בלי devDependencies), `migration:revert` (מבטל את האחרון) ו-`migration:show` (מציג מה הוחל). מריצים `migration:run` לפני שמעלים build חדש בכל מקום חוץ ממכונה מקומית עם `DB_SYNCHRONIZE=true`, שם `synchronize` מוסיף את אותם אובייקטים בעלייה וה-migration הופך ל-no-op. האפליקציה לא מריצה migrations בעצמה (אין `migrationsRun`): שינוי סכמה הוא צעד מכוון, לא תופעת לוואי של restart. TypeORM שומר את רשימת ה-migrations שהוחלו בטבלה `migrations` שהוא יוצר בהרצה הראשונה.

שני migrations בינתיים, שניהם עם `IF NOT EXISTS` ועם `down` שמבטל, שניהם רק מוסיפים אובייקטים (שום דבר לא נמחק, הטבלאות של הגרסה הקודמת אמורות להיות קיימות), ובשניהם טיפוסי העמודות ושמות ה-constraints זהים למה ש-`synchronize` מייצר מה-entities, אז מסד מקומי שעבר באחת הדרכים לא מראה הבדל מול השנייה:

- `OfflineSync1790600000000`: `issuances.revision`, `delivery_attempts.client_reported_at` והטבלה `delivery_operations` עם האינדקס הייחודי שלה.
- `ConflictEvidence1790800000000`: הטבלה `delivery_conflicts` עם אינדקס ייחודי על (`user_id`, `operation_id`) ומפתח זר ל-`delivery_tasks`. שמות ה-constraints מגיעים מאסטרטגיית השמות של TypeORM בתוך ה-migration עצמו.
- `NoRecipientWithoutDelivery1790900000000`: `delivery_attempts.recipient_type`, `delivery_conflicts.recipient_type` ו-`delivery_conflicts.signature_png` הופכות ל-nullable, לדוח שכל שורותיו "לא נמסר" (אף אחד לא קיבל, אף אחד לא חתם). `DROP NOT NULL` הוא no-op איפה ש-`synchronize` כבר עשה את זה. ה-revert מחזיר את האילוצים ו-PostgreSQL מסרב לו כל עוד יש שורות כאלה.

## עבודה ללא רשת

כניסה למערכת דורשת שרת. מרגע הכניסה מסכי המשנע רצים מנתונים מקומיים, עם רשת או בלעדיה: הלוח עם הלשוניות, המונים, החיפוש והקיבוץ, מסך ההנפקה עם הקודם / הבא, האיתור הידני, טופס הדיווח וכפתור השליחה. לצד המנהל אין מצב ללא רשת.

**מה יורד למכשיר.** רשימת המשימות המלאה, `GET /delivery/tasks?tab=all` בלי חיפוש, שכבר מכילה את ההנפקה והפריטים שלה לכל משימה, כך שלמשימה ממתינה שהמשנע מעולם לא פתח יש כל מה שטופס הדיווח צריך. הרשימה מוחלפת כולה בטרנזקציה אחת אחרי בדיקת צורה: השורות חייבות להיות מערך של משימות עם מזהים מספריים ו-`counts.all` חייב להיות שווה למספר השורות, ההוכחה הזולה שהתשובה שלמה ולא מסוננת. רענון שנכשל או חוזר פגום משאיר את התמונה הקודמת, רושם את השגיאה ומציג "הרענון נכשל" בלוח. פרטי הדיווח של משימה שהושלמה (תשובות הפריטים והחתימה; לשורות הרשימה אין אותם) נמצאים במכשיר רק אם המשימה נפתחה מקוונת במכשיר הזה (`GET /delivery/tasks/:id` נשמר אז) או דווחה ממנו; אחרת מסך ההנפקה מציג "פרטי הדיווח לא הורדו למכשיר" במקום בלוק הדיווח.

רענון רץ כשמסכי המשנע נפתחים, בכפתור רענון ברצועת הסטטוס, אחרי סבב סנכרון שמסר לפחות דוח אחד, ובאופן מוגבל כשהאפליקציה חוזרת לקדמה או כשהרשת חוזרת (לכל היותר פעם בדקה; הלוח גם מרענן בעלייה כשהתמונה בת יותר מחמש דקות). הרצועה אומרת "מכין נתונים לעבודה ללא רשת..." עד שהתמונה הראשונה נשמרה, ו"מוכן לעבודה ללא רשת, עודכן ב-HH:MM" אחר כך.

**המסד המקומי.** IndexedDB בשם `es-courier`, גרסה 1, דרך הספרייה `idb` (`client/src/courier/offline/db.ts`):

| מאגר | מפתח | מה יש בו |
| --- | --- | --- |
| `meta` | `scope` | מוכנות, זמן הרענון האחרון, השגיאה האחרונה, תשובת האחסון הקבוע, החכירה בין לשוניות |
| `tasks` | `[scope, task_id]` | שורות ההורדה האחרונה של הרשימה עם המיקום שלהן |
| `task_details` | `[scope, task_id]` | גוף הפרטים של משימות שהושלמו ונפתחו מקוונות |
| `drafts` | `[scope, task_id]` | טופס של דוח שעדיין ממלאים: תשובות, מקבל, PNG של החתימה והמשיכות |
| `reports` | `[scope, operation_id]` | דוחות חתומים שממתינים לשרת או נדחו על ידו, עם מצב הסנכרון ואישור השרת |

`scope` הוא `<users.id>:<couriers.id>`; כל מפתח מתחיל בו, כל פונקציה בשכבת הנתונים מקבלת אותו וזורקת על scope ריק, אז שום דבר לא נשמר תחת חשבון לא מוגדר. שני חשבונות באותו מכשיר לא רואים זה את השורות של זה. הקריאה החוצה-scope היחידה היא רשימת החשבונות האחרים עם עבודה בתור, בשביל ההודעות. התנתקות מנקה localStorage בלבד, המסד שומר הכל. גרסת סכמה עתידית מוסיפה מאגרים ואינדקסים במקום ולעולם לא מוחקת מאגר, כי ייתכן שיושב בו דוח שעוד לא הגיע לשרת.

**ארבעה סוגי נתונים.** הם לא מתערבבים: תמונת השרת (`tasks`, `task_details`, מוחלפת בכל רענון), הטיוטה (`drafts`, העבודה שעוד לא נשלחה), הדוח הקפוא (`reports`, קפוא ברגע הלחיצה על שליחה; רק מצב הסנכרון והאישור משתנים אחר כך), והתצוגה, שמחושבת בקריאה: משימה ממתינה בתמונה עם דוח במצב queued / syncing / synced / auth מוצגת כהושלמה עם הניסיון המקומי (תשובות, מקבל, חתימה), סטטוס ההנפקה שלה הוא תוצאת הדוח והלוח סופר אותה תחת הושלם; משימה שהדוח שלה נדחה נשארת כמו בתמונה ומקבלת צ'יפ טיפול; משימה שהושלמה בתמונה שומרת את `local_report` בכל מצב, כך שהצ'יפ שורד רענון. כרטיס בלוח מציג את הצ'יפ רק כל עוד הדוח עדיין במכשיר או נדחה; לדוח שהשרת קיבל אין צ'יפ בלוח, מסך ההנפקה אומר "התקבל בשרת". מוני הלשוניות מחושבים על כל הקבוצה אחרי השכבה, לא על תוצאות החיפוש, כמו בשרת.

**טיוטות.** כל שינוי בטופס נכתב למכשיר 600 מילישניות אחרי ההקשה האחרונה, ומיד כשהעמוד מוסתר, נפרק או עוזבים אותו. החיווי אומר "טיוטה נשמרה במכשיר" רק אחרי שהטרנזקציה בוצעה. משיכות חתימה שהושלמו הן חלק מהטיוטה והפד מצייר אותן מחדש בפתיחה הבאה (נגיעה בודדת היא נקודה, שמצוירת, נשמרת ונשלחת באותה צורה). כתיבת טיוטה נדחית ברגע שקיים דוח למשימה במצב פעיל, כך שטיימר מאוחר לא יכול להחזיר טיוטה אחרי שליחה. "ניקוי הטיוטה" מנקה גם את הטיוטה וגם את הטופס.

**שליחת דוח.** אותו מסלול עם רשת ובלעדיה: ולידציה, יצירת מזהה פעולה (`crypto.randomUUID`, או v4 מ-`getRandomValues` על http רגיל), כתיבת הדוח ומחיקת הטיוטה בטרנזקציה אחת, ורק אז עדכון המסך והערת ה-worker. משימה עם דוח פעיל מסרבת לדוח שני ("לדוח של הנפקה זו יש שליחה שממתינה לשרת"). כתיבה מקומית שנכשלת מציגה את סיבת האחסון (אין מקום, אחסון לא זמין, או שמירה שנכשלה) ולא מצב "נשמר". שני סיומים שונים: "הדוח נשלח" רק כשאישור השרת מגיע תוך ארבע שניות, אחרת "הדוח נשמר במכשיר וישלח לשרת כשיהיה חיבור" (וגם מיד כשהמכשיר מנותק או ממתין להתחברות). דוח שהשרת דוחה בתוך ארבע השניות משאיר את הטופס על המסך עם התשובות והתראה שאומרת מה השרת אמר.

**מצבי הסנכרון** (`ReportSyncState` ב-`shared/@core.ts`), ציר נפרד מהסטטוס העסקי, שהוא תוצאת הדוח:

| מצב | משמעות | ניסיון חוזר |
| --- | --- | --- |
| `queued` | נשמר במכשיר, ממתין לרשת או לסיום ה-backoff | אוטומטי, ו"נסה שוב" מאפס את ה-backoff |
| `syncing` | בקשה בדרך | |
| `synced` | השרת אישר, האישור שמור ליד הדוח | |
| `auth` | השרת ענה 401, או שהטוקן השמור חסר, פג או שייך לחשבון אחר | אחרי כניסה של אותו חשבון |
| `invalid` | 400, השרת דחה את התוכן; ההודעה נשמרת | לא, הבדיקה ידנית |
| `forbidden` | 403 או 404, המשימה כבר לא של המשנע הזה | לא |
| `conflict` | 409, המשימה השתנתה מתחת לדוח; הקוד אומר איך (ראו "דוחות שלא נקלטו") | לא |

רק `queued` ו-`auth` ניתנים לניסיון חוזר ידני. תקלות רשת, timeout, 408 / 425 / 429, 5xx ו-2xx שהגוף שלו לא נראה כמו תשובה חוזרים ל-`queued` עם backoff (30 שניות שמוכפלות עד 15 דקות, ועוד עד 30% אקראי); חיבור חוזר, פתיחת האפליקציה וכניסה למערכת מאפסים את ה-backoff של תקלות רשת, סטטוסים שהשרת באמת ענה שומרים על שלהם.

**ה-worker של הסנכרון** (`client/src/courier/offline/sync.ts`) רץ כל עוד מסכי המשנע פתוחים, אחד לחשבון, ורק בקדמה. אין Background Sync ושום דבר לא מובטח כשהאפליקציה או הדפדפן סגורים: הדוחות יוצאים בפעם הבאה שהאפליקציה פתוחה עם רשת והתחברות תקפה. סבב רץ בהפעלה, אחרי כל שליחה, בניסיון חוזר ידני, כשהרשת חוזרת, כשהלשונית נהיית גלויה או מקבלת פוקוס, כשלשונית אחרת מבקשת, וכל 60 שניות כל עוד משהו בתור או שהבקשה האחרונה נכשלה (`navigator.onLine` הוא רמז בלבד, בקשה אמיתית היא ההוכחה). בקשות נקטעות אחרי 20 שניות. דוחות יוצאים לפי סדר הכניסה לתור, אחד אחד; דוח שלא הגיע ל-`synced` עוצר את הדוחות המאוחרים של אותה משימה באותו סבב, ומשימות אחרות ממשיכות. לשונית אחת שולחת בכל רגע: הסבב לוקח Web Lock (או חכירה ב-`meta` איפה שאין Web Locks), לעולם לא לכל חיי ה-worker, ולשונית שלא הצליחה לקבל אותו מבקשת מהמחזיקה להריץ סבב דרך `BroadcastChannel`, שגם מודיע לשאר הלשוניות לקרוא מחדש אחרי כל כתיבה מקומית. תוצאה שמגיעה אחרי התנתקות או אחרי מעבר לחשבון אחר נזרקת. אחרי דוחות המסירה של סבב ה-worker מעלה את הראיות של דוחות שנדחו וקורא את סטטוס הבדיקה של אלה שכבר בשרת, ראו "דוחות שלא נקלטו".

**אחסון קבוע.** `navigator.storage.persist()` מתבקש פעם אחת בסשן והתשובה מוצגת בתחתית מודל הדוחות. זו בקשה, לא הבטחה: "clear site data", ניקוי ידני של נתוני הגלישה או פינוי שהדפדפן מחליט עליו בעצמו עדיין מוחקים הכל, כולל דוחות שבתור.

**אימות והטוקן של 12 שעות.** ה-JWT תקף 12 שעות; הנתונים המקומיים לא פגים איתו. עם טוקן שפג הלוח, המשימות, הטיוטות והדוחות השמורים נשארים קריאים, ואפשר עדיין לחתום דוח ולהכניס אותו לתור. שליחה דורשת טוקן תקף של אותו חשבון: 401, או טוקן שחסר, פג או שייך למישהו אחר, מחנה את כל הדוחות שבתור במצב `auth` בלי לשלוח כלום, הרצועה מציגה "נדרשת התחברות מחדש" ולחיצה עליה עוצרת את ה-worker, מנקה localStorage ופותחת את עמוד הכניסה. כניסה חוזרת של אותו חשבון מרימה את התור לבד. חשבון אחר שנכנס באותו מכשיר רואה "במכשיר יש N דוחות של X שטרם נשלחו לשרת" בעמוד הכניסה וברצועה, וה-worker שלו לעולם לא שולח אותם: ה-`sub` של הטוקן מושווה למזהה המשתמש של הדוח לפני כל בקשה, ורענון רקע או הבאת פרטים של scope נדחים תחת טוקן של חשבון אחר, כך שלשונית שנשארה על החשבון הראשון לא יכולה לדרוס את התמונה שלו. לשונית עוקבת אחרי כניסה או התנתקות שנעשו בלשונית אחרת (אירוע `storage`) ומפעילה מחדש את ה-worker לחשבון החדש. התנתקות עם דוחות בתור או דוחות שנדחו מבקשת אישור קודם ואומרת שהדוחות נשארים במכשיר.

**רצועת הסטטוס.** מתחת לכותרת המשנע: החיבור (מחובר / אין חיבור לרשת / השרת לא זמין כרגע), הנתונים (מוכן וזמן הרענון, או מכין, או לא הורדו), כפתור רענון, פעולת ההתחברות מחדש כשצריך, התור ("דוח אחד ממתין לסנכרון", "מסנכרן...", "כל הדוחות התקבלו בשרת", או "דוחות שנשמרו במכשיר" לפתיחת הרשימה), מונה הדוחות שדורשים טיפול, ושתי הודעות: עבודה בתור של חשבון אחר, ו"עבודה ללא רשת לא זמינה בכתובת הזו" בעמוד שאינו secure context. כרטיסים בלוח נושאים צ'יפ קטן ליד תג הסטטוס למשימה שהדוח המקומי שלה עוד לא הגיע לשרת (נשמר במכשיר) או נדחה (הדחייה); לדוח שסונכרן אין צ'יפ בלוח, רק במסך ההנפקה.

### דוחות שלא נקלטו

דוח שהשרת דחה (`invalid`, `forbidden`, `conflict`) נשאר במכשיר ללא הגבלת זמן: שום דבר לא גוזם אותו, אין פעולת מחיקה, ורענון לא נוגע בו גם כשהמשימה שלו יצאה מהרשימה. הוא מופיע תחת "דורשים טיפול" במודל הדוחות וניתן לקריאה מלאה ב-`/courier/reports/:operationId`: לקוח, כתובת, תשובה לכל פריט עם הסיבה, המקבל, החתימה, מצב הסנכרון והודעת השרת, ובנוסף "ההנפקה כבר לא מופיעה בלוח שלך" כשהמשימה נעלמה.

`conflict` (409 מנתיב הדיווח) נמסר גם לשרת כראיה, בלי שיוחל אי פעם. שלושה דברים מופרדים, בטאבלט ובניסוח:

1. דוח מסירה שהתקבל והוחל: `ReportSyncState.synced`, שורה ב-`delivery_operations`, ניסיון, משימה סגורה.
2. דוח שנדחה ונשמר בשרת לבדיקת המנהל: `ReportSyncState.conflict` עם `EvidenceUploadState.received` או `reviewed`, שורה ב-`delivery_conflicts`, בלי ניסיון ובלי שינוי במשימה או בהנפקה.
3. דוח שנדחה ושמור עדיין רק במכשיר: `ReportSyncState.conflict` עם `EvidenceUploadState.none`, `pending`, `uploading` או `failed`. עד שההעלאה מצליחה הוא תלוי באחסון המכשיר כמו כל שורה מקומית אחרת.

העלאת הראיות רצה בסבב של ה-worker, מיד אחרי דוחות המסירה, דרך `POST /delivery/tasks/:id/conflicts` עם אותו גוף שנתיב הדיווח סירב לו (כולל `operation_id`, `issuance_revision` ו-`client_reported_at`). היא משתמשת בכללי התור: הטוקן הנוכחי חייב להיות של חשבון הדוח, תקלת רשת או 5xx נדחים ב-backoff (30 שניות שמוכפלות עד 15 דקות) שחיבור חוזר מאפס, 401 עוצר בלי לגעת בשורה, העלאה שנכשלה לעולם לא מעכבת דוח מסירה, ולשונית אחת שולחת בכל רגע. תשובות 400, 403, 404 ו-409 מסמנות את ההעלאה כ-`failed` ומשאירות את השורה לטיפול; "שליחה חוזרת לבדיקה" שולחת שוב ביד. דוח המסירה שנדחה לא נשלח שוב אף פעם כדרך להעלות ראיות. קונפליקטים שנרשמו לפני הגרסה הזו (שורות בלי שדה `evidence`) מועלים כמו כל אחד אחר; מבנה ה-IndexedDB לא השתנה בשביל זה (עדיין גרסה 1, השדה אופציונלי). "התקבל בשרת לבדיקת המנהל" מופיע רק אחרי שהקבלה (`kind: "conflict_recorded"`, עם `conflict_id` ו-`received_at`) נכתבה לשורה המקומית. בכל סבב מאוחר יותר ה-worker שואל `GET /delivery/conflicts?operation_ids=` על השורות שהתקבלו ומעביר את מה שמנהל בדק ל"נבדק על ידי המנהל ב-...", מה שגם מוציא אותן מספירת הדוחות שדורשים טיפול (הן נשארות ברשימה תחת "נבדקו על ידי המנהל", ובמכשיר). השורות בעברית, לפי הסדר: "הראיות שמורות רק במכשיר הזה", "ממתין לשליחה לבדיקת המנהל", "נשלח לבדיקת המנהל...", "התקבל בשרת לבדיקת המנהל ב-...", "נבדק על ידי המנהל ב-.... דוח המסירה לא הוחל על המשלוח.", "שליחת הראיות לבדיקה נכשלה: ...".

בשרת ההעלאה עוברת ולידציה כמו דוח מסירה (PNG אמיתי עד 1MB, גוף עד 2MB, כללי המקבל, שניהם אופציונליים כשכל השורות סורבו, תשובה בוליאנית אחת לכל שורה עם סיבה רק בשורה שלא נמסרה) חוץ מזה שהתשובות לא מותאמות לשורות ההנפקה הנוכחיות: הן מה שנחתם, והשורות אולי השתנו מאז. ואז ההחלטה נופלת תחת אותן נעילות כמו נתיב הדיווח (הנפקה, ואז משימה). הצלחה שמורה לאותה פעולה מנצחת ומוחזרת כ-`{ kind: "delivered", ...IAttemptResult, replayed: true }`: מכשיר שאיבד 201 לעולם לא רושם קונפליקט שקרי. קונפליקט שמור מחזיר את הקבלה שלו. דוח שעדיין אפשר להחיל (משימה פתוחה, הנפקה משויכת, revision עדכני) נדחה ב-409 `not_a_conflict` ושום דבר לא נרשם. כל השאר נרשם פעם אחת עם המצב שנצפה באותו רגע (`observed`: סטטוס המשימה, סטטוס ו-revision של ההנפקה, המשימה הפתוחה והמשנע שלה אם יש, הניסיון שסגר את המשימה אם יש); אותו מזהה עם תוכן אחר הוא 409 `operation_reused`; אינדקס ייחודי על (`user_id`, `operation_id`) ואותה קריאה חוזרת אחרי rollback כמו ב-`delivery_operations` מכסים שתי העלאות במקביל. בלי אימות, בתפקיד לא נכון, על משימה של משנע אחר או עם גוף פגום לא נוצרת שורה (401, 403, 404, 400). חתימות לעולם לא נמצאות בתשובות רשימה או בשורות לוג.

המנהל קורא את הראיות תחת "דוחות לבדיקה" (`/manager/conflicts`, `GET /conflicts` עם דפדוף, ממתינים או נבדקו): הנפקה, משנע, סיבה, זמן המכשיר, זמן השרת, בדיקה. פתיחת שורה (`GET /conflicts/:id`) טוענת את החתימה ואת התשובות לצד שני מצבים: מה שנרשם ברגע הדחייה ומה שיש עכשיו (סטטוס ו-revision של ההנפקה, כל המשימות שלה עם המשנע של כל אחת, הניסיון שסגר בפועל את המשימה של הדוח שנדחה, בלי החתימה שלו). "סימון כנבדק" (`POST /conflicts/:id/review`) דורש הערה ואת ה-`review_version` שהמסך טען; הוא שומר את הבודק ואת הזמן ולא יותר. שורה שמנהל אחר כבר בדק עונה 409 `review_conflict` עם הבדיקה ההיא במקום לקבל הערה שנייה מעליה, גרסה ישנה נדחית באותה דרך, ואותו מנהל שחוזר על אותה הערה מקבל את אותה תשובה. הבדיקה לא משנה את המשימה, את הניסיון, את ההנפקה ואת הראיות שנמסרו, והיא מסומנת כבדיקה, לעולם לא כאישור: אין כאן החלה בכוח, מיזוג, שיוך מחדש או פתיחה מחדש. המשנע רואה רק את הסטטוס של השורות שלו (`GET /delivery/conflicts`), לא את ההערה, ולעולם לא ראיות של משנע אחר. שורות ב-`delivery_conflicts` לא נמחקות על ידי האפליקציה.

קודי ההתנגשות ומה הטאבלט אומר:

| `code` | מתי | בעברית |
| --- | --- | --- |
| `task_closed` | המשימה כבר דווחה, ממכשיר אחר או דרך מזהה פעולה שני | ההנפקה כבר דווחה ממכשיר אחר |
| `task_cancelled` | המשימה בוטלה בינתיים: שיוך מחדש, איסוף עצמי, מחיקה | ההנפקה הועברה למשנע אחר, לאיסוף עצמי או נמחקה |
| `issuance_not_assigned` | ההנפקה כבר לא בסטטוס `assigned` | ההנפקה כבר לא בסטטוס שמאפשר דיווח |
| `revision_changed` | ה-revision של ההנפקה זז מאז ההורדה | פרטי ההנפקה השתנו מאז ההורדה למכשיר |
| `operation_reused` | אותו מזהה פעולה כבר שימש עם תוכן אחר | מזהה הדיווח כבר בשימוש עם תוכן אחר |

שיוך מחדש לאותו משנע (המנהל מזיז תאריך על ידי שיוך נוסף) יוצר משימה חדשה ומבטל את הישנה, אז דוח שבתור מול המשימה הישנה הוא התנגשות `task_cancelled` בכוונה: דוח בתור לעולם לא מופנה למשימה שזה עתה שויכה, המשנע חתם על המשימה ההיא והמנהל מחליט מה המשימה החדשה אומרת.

דוחות שסונכרנו נשמרים 30 יום אחרי האישור כדי שמסך ההנפקה יוכל להציג את החתימה בלי רשת, ואז נגזמים ברענון הבא, או מוקדם יותר כשהמשימה שלהם יוצאת מהרשימה.

### מה מבטל דוח

`issuances.revision` (מספר שלם, ברירת מחדל 1) הוא אסימון המקביליות. הוא מקודם, בתוך הטרנזקציות הנעולות הקיימות, על ידי שיוך, איסוף עצמי, מחיקה ודיווח מסירה. עריכת עדיפות, מועד חלוקה והערות וסימון כדחוף לא מקדמים אותו: הם לא מזיקים לדוח, ודוח שנכתב לפני עריכה כזו עדיין מוחל. הטאבלט שומר את ה-revision עם התמונה ושולח אותו חזרה עם הדוח; מספר אחר הוא 409 עם `revision_changed` ושום דבר לא נכתב.

היום כל קידום גם מבטל או סוגר את המשימה, אז בדיקת המשימה יורה קודם (`task_cancelled` / `task_closed`) ואי אפשר להגיע לבדיקת ה-revision בזרימה אמיתית. זה שומר לעתיד למקורות קידום שלא נוגעים במשימה, כמו שינויי פריטים או לקוח מ-SAP כשהממשק הזה יהיה קיים; בדיקת ה-e2e שולחת מספר ישן מפוברק כדי לכסות אותו. חותמות זמן מהלקוח לא משתתפות בפתרון התנגשויות: `client_reported_at` נשמר לתיעוד, `reported_at` נשאר זמן הקליטה בשרת.

שני דברים ששווה לדעת כשמוסיפים CSS: כלל עם class אחד על רכיב MUI מפסיד בתיקו לסגנון של MUI (הוא מוזרק אחרי הגיליון שלנו), אז לרכיבי MUI כותבים selector עם שני classes, למשל `.issuance-card__menu.MuiIconButton-root`. ו-`overflow-x` יושב על `html` בלבד: על `body` הוא היה הופך אותו למכולת גלילה והורג כל `position: sticky`.

## HTTPS ובדיקת הגרסה הבנויה

Service workers, `crypto.randomUUID`, Web Locks ו-`navigator.storage.persist` קיימים רק ב-secure context: https, או `localhost`. טאבלט שפותח `http://<lan-ip>:5173` (הסיבה ל-`server.host: true` ב-`vite.config.ts`) לא מקבל אף אחד מהם: רצועת הסטטוס אומרת "עבודה ללא רשת לא זמינה בכתובת הזו", טעינה מחדש בלי רשת לא עובדת, והחלופות נכנסות לשאר (uuid v4 מ-`getRandomValues`, החכירה ב-`meta` במקום Web Lock, בלי בקשת אחסון קבוע). שכבת הנתונים וה-worker עדיין עובדים שם, אז דוחות נכנסים לתור ונשלחים; מה שחסר הוא מעטפת האפליקציה בלי רשת.

כדי לבדוק על טאבלט נותנים לשרת הפיתוח או ל-preview תעודה. עם [mkcert](https://github.com/FiloSottile/mkcert):

```bash
mkcert -install
mkcert localhost 192.168.1.20     # כתובת ה-lan של המחשב, הקבצים נוצרים בתיקייה הנוכחית
```

מכוונים את `CLIENT_TLS_KEY` ו-`CLIENT_TLS_CERT` לשני הקבצים (ב-PowerShell: `$env:CLIENT_TLS_KEY="...\localhost+1-key.pem"`, `$env:CLIENT_TLS_CERT="...\localhost+1.pem"`) ומריצים `npm run dev` או `npm run preview`; `vite.config.ts` מדליק https לשניהם כששני הקבצים קיימים, ומשאיר כבוי אחרת. הטאבלט צריך את ה-root של mkcert מותקן כדי לסמוך על התעודה.

ה-service worker נרשם רק בגרסה הבנויה, אז את המעטפת ללא רשת בודקים מול ה-build:

```bash
cd client && npm run build && npm run preview
```

`npm run preview` מגיש את `dist/` ב-http://localhost:4173 ומעביר `/api` לשרת ה-NestJS בפורט 3000 (ה-proxy של ה-preview הוא אותו אובייקט כמו של הפיתוח; `API_PROXY_TARGET=http://localhost:3002` מכוון את שניהם למופע אחר, למשל כזה שהורץ עם `DB_NAME=equipment_supply_test PORT=3002`, כך שבדיקה בדפדפן לא נוגעת בנתוני הפיתוח). ואז: נכנסים כמשנע, מחכים ל"מוכן לעבודה ללא רשת" ברצועה, פותחים DevTools, Network, Offline, וטוענים מחדש את `/courier` ואת `/courier/tasks/:id` ישירות; שניהם מגיעים מה-service worker ומהמסד המקומי. `/api` מוחרג מה-fallback של ניווט ל-HTML ושום תשובת API לא נשמרת ב-worker; הנתונים של המשנע חיים רק במסד שמופרד לפי חשבון.

עדכוני service worker אוטומטיים ושקטים: build חדש יורד ברקע ומוחל בטעינה מחדש ברגע שהוא במכשיר, בלי לשאול את המשנע ובלי להציג דבר. החריג היחיד הוא טופס דיווח פתוח (`TaskDetailPage` על משימה פתוחה מחזיק את העדכון דרך `holdUpdate` ב-`client/src/courier/offline/sw.ts`): ה-build ממתין ומוחל ברגע שעוזבים את המסך או שהמשימה נסגרת, כך שחתימה באמצע ציור לא נעלמת. טיוטות ודוחות בתור שמורים ב-IndexedDB ושורדים את הטעינה מחדש; בקשה שהייתה באוויר נשלחת שוב עם אותו operation id בהפעלה הבאה של ה-worker. ל-manifest (`name`, `short_name`, `lang: he`, `dir: rtl`, `start_url: /courier`, `display: standalone`) יש אייקון SVG אחד, `client/public/icon.svg` (הסמל בלבן על הכחול הראשי, ריבועי כי באנר ההתקנה של Chrome מסרב לצורות אחרות). לא נוצרו אייקוני PNG ולא אייקון למסך הבית של iOS; iOS מתעלם מאייקוני manifest.
